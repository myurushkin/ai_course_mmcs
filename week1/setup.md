# Рабочее окружение: как мы работаем в курсе

Цель недели: к следующему вторнику у каждого на своей машине работает окружение, в котором домашние задания делаются вместе с агентом для кода, а не вручную в Colab.

Порядок чтения: сначала разделы 1–4 (обязательно), потом 5–7 по потребности.

---

## 1. Что понадобится

- Ноутбук с любой ОС. На Windows удобнее работать через WSL2 (Ubuntu), но не обязательно.
- Python 3.12 или новее, git, VS Code.
- Аккаунт GitHub: репозиторий команды живёт там.
- Ключи к моделям: сервис с OpenAI-совместимым API, доступный из России без VPN и с оплатой в рублях (конкретный выбирает преподаватель). В окружении держим три переменные: `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `MODEL`. Лимит расходов ставится сразу, до первого запуска агента.
- Проверка сервиса: `python check_provider.py` из `week2/practice` делает один запрос и показывает, умеет ли модель вызывать инструменты в формате `tool_calls` и приходит ли `usage`. Без этих двух вещей задания курса не поедут.
- Агент для кода: Claude Code, Codex или любой другой на ваш выбор. Курс не привязан к конкретному продукту; примеры ниже нейтральны и переносятся между ними.

## 2. Python и виртуальные окружения: uv

**Зачем.** Каждый проект использует свой набор библиотек и их версий. Если ставить всё в системный Python, версии начнут конфликтовать между проектами и с самой системой. Виртуальное окружение — отдельная папка с интерпретатором и пакетами только для этого проекта.

**Инструмент курса — uv.** Это менеджер Python-проектов: ставит нужную версию Python, создаёт окружение, ставит пакеты и фиксирует версии в lock-файле, и делает это быстро. Он заменяет связку `pyenv` + `venv` + `pip` + `pip-tools`.

Установка (Linux, macOS, WSL):

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

На Windows без WSL — установщик с сайта uv (docs.astral.sh/uv) или `winget install astral-sh.uv`.

Новый проект:

```bash
uv init my-agent            # создаёт pyproject.toml и структуру
cd my-agent
uv python install 3.12      # при необходимости ставит нужный Python
uv add google-adk openai python-dotenv   # зависимости пишутся в pyproject.toml, версии — в uv.lock
uv run python main.py       # запуск внутри окружения, активировать ничего не надо
uv add --dev pytest && uv run pytest
```

Что важно понимать:
- `pyproject.toml` — список зависимостей проекта, `uv.lock` — точные версии; оба файла коммитятся, папка `.venv` — нет.
- `uv run …` запускает команду в окружении проекта. Если привычнее активировать окружение: `source .venv/bin/activate`.
- Один проект — одно окружение. Ноутбуки Jupyter тоже запускаются из него.

Если uv по какой-то причине не подходит, эквивалент стандартными средствами: `python -m venv .venv`, `source .venv/bin/activate`, `pip install -r requirements.txt`. Требование курса — воспроизводимое окружение с зафиксированными версиями, инструмент на ваш выбор.

## 3. VS Code

Редактор курса — VS Code: бесплатный, работает везде, умеет ноутбуки и удалённую работу. Другие редакторы не запрещены, но материалы и подсказки будут про него.

Поставить и настроить:
1. Установить VS Code, открыть папку проекта (`File → Open Folder`).
2. Расширения: **Python** и **Jupyter** (обе от Microsoft). После этого `.ipynb` открываются и выполняются прямо в редакторе — Colab для этого не нужен.
3. Выбрать интерпретатор проекта: `Ctrl+Shift+P → Python: Select Interpreter → .venv` (uv создаёт его в папке проекта).
4. Встроенный терминал (`` Ctrl+` ``) — там живут `uv`, `git` и агент для кода.

Полезное: `Ctrl+Shift+P` — палитра команд, `Ctrl+P` — быстрый переход к файлу, `F5` — отладчик, вкладка Source Control — git без командной строки.

## 4. Агент для кода: как мы с ним работаем

Агент для кода — это программа, которая по вашей задаче словами читает репозиторий, правит файлы, запускает команды и тесты, и показывает результат. Именно такие системы мы изучаем в курсе, поэтому пользоваться ими на домашних заданиях не просто разрешено, а ожидается.

**Пример: Codex.** Устанавливается как CLI (`npm install -g @openai/codex`, затем `codex` и вход через аккаунт ChatGPT) или как расширение для VS Code. Запускается в папке проекта. Три вещи, которые надо настроить в первый день:
- **Файл `AGENTS.md`** в корне репозитория: короткие инструкции агенту — как ставить зависимости (`uv sync`), как запускать тесты (`uv run pytest`), где лежат данные, что не трогать. Это оглавление для агента, а не энциклопедия: страница текста, не больше.
- **Режим подтверждений.** У агента есть уровни: показывать изменения и спрашивать перед каждым действием, править файлы самостоятельно и спрашивать перед командами, работать автономно в песочнице. Начните с подтверждений, переходите к автономному режиму, когда поймёте, что он делает.
- **Песочница.** Агент выполняет команды в изолированном окружении с ограничениями на файлы и сеть. Не отключайте их, чтобы «было удобнее»: именно они спасут репозиторий от `rm -rf` по ошибке.

**Как ставить задачи, чтобы получалось.**
- Маленькие шаги с проверяемым результатом: «добавь инструмент `district_stats` с тестом на пустой район», а не «сделай агента».
- Сначала тесты или пример ожидаемого результата, потом реализация: агенту нужно, обо что проверяться.
- Читайте дифф перед принятием. Вы отвечаете за код, а не агент.
- Если агент ходит по кругу — остановите, уточните задачу или сделайте шаг руками. Это нормально.

**Правило курса.** В каждом отчёте — раздел «что делал агент, что проверял я». На защите вы объясняете любую строку своего кода. Не смогли объяснить — работа не засчитывается.

Другие агенты для кода (Cursor, Gemini CLI, Copilot и т.д.) работают по тем же принципам: инструкции в репозитории, режим подтверждений, маленькие задачи с тестами.

## 5. Ключи и секреты

- Ключи лежат в файле `.env` в корне проекта: `GEMINI_API_KEY=…`, `OPENAI_API_KEY=…`, `HF_TOKEN=…`. Файл `.env` — в `.gitignore`, в репозиторий кладётся только `.env.example` без значений.
- В коде ключи читаются через `python-dotenv` или переменные окружения, никогда не пишутся в исходники и ноутбуки.
- У платных провайдеров поставьте лимит расходов в личном кабинете до первого запуска агента: цикл с ошибкой может сделать сотни вызовов.
- Агент для кода видит ваш репозиторий. Если ключ попал в файл, который агент может прочитать и отправить, считайте его скомпрометированным и перевыпустите.

## 6. Удалённая работа: VS Code Remote и общая машина

**Зачем.** Слабый ноутбук, нужен Linux, общая машина курса, арендованный сервер или GPU — во всех этих случаях код лежит и запускается на удалённой машине, а редактор с агентом остаются у вас.

**Как.** Расширение **Remote – SSH** в VS Code: `Ctrl+Shift+P → Remote-SSH: Connect to Host`, указываете `user@host`. Дальше VS Code работает так, будто папка локальная: терминал, ноутбуки, расширения и агент для кода выполняются на удалённой машине. Ключи SSH настраиваются один раз (`ssh-keygen`, `ssh-copy-id user@host`).

**Проброс портов.** Если на удалённой машине запущен веб-интерфейс или локальный сервер на порту, скажем, 8791, VS Code пробрасывает его автоматически или через панель Ports: открываете `http://localhost:8791` у себя. Так же можно вручную: `ssh -L 8791:127.0.0.1:8791 user@host`.

**Общая машина курса** (если выделена): вход по SSH под своим пользователем, своё uv-окружение в своей папке, свои ключи в своём `.env`. Общая машина — для работы с моделями через API и для запуска агентов; тяжёлые вычисления и обучение на ней не запускаем.

## 7. Когда нужен GPU

Для большинства недель GPU не нужен: модели вызываются через API. Он понадобится в двух местах: измерения инференса на открытой модели и дообучение. Варианты:
- **Google Colab или Kaggle**: бесплатный T4, ноутбук `.ipynb` тот же, что вы делаете локально в VS Code; хватит для моделей до 1–3 млрд параметров и LoRA.
- **Аренда GPU** (vast.ai и аналоги): для моделей побольше и vLLM; подключение по SSH и VS Code Remote из раздела 6; правило «поднял → сделал → погасил».

Агенты для кода в Colab не работают, поэтому подготовку ноутбука делайте локально с агентом, а в Colab только запускайте.
